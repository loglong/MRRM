# Domain Pitfalls: 医疗患者关系管理系统 (MRRM)

**Domain:** 医疗CRM / 患者关系管理系统
**Project:** MRRM - 医疗患者关系管理系统
**Researched:** 2026-03-25
**Confidence:** MEDIUM (based on domain knowledge; unable to verify with current web sources due to search API unavailability)

## Critical Pitfalls

Mistakes that cause rewrites, compliance violations, or major patient data issues.

---

### Pitfall 1: 患者数据模型过度简化

**What goes wrong:** 将患者视为简单的"客户"记录，忽略医疗数据的复杂性。

**Why it happens:** 传统CRM思维主导，将患者当作"客户"而非"患者"对待。忽视了：
- 过敏史、既往病史、用药史等医疗核心数据
- 治疗方案、手术记录、检查报告等临床数据结构
- 随访周期、复诊提醒等医疗业务逻辑

**Consequences:**
- 随访计划无法与治疗方案关联
- 患者安全风险（药物过敏未记录）
- 医疗质量无法追踪
- 后续无法支持健康管理中心功能

**Prevention:**
- 设计以"患者健康档案"为核心的数据模型
- 预留医疗数据结构化扩展字段
- 咨询医疗业务专家而非仅依赖产品经理

**Detection:**
- 开发初期review数据模型时是否有医疗专业人员参与
- 随访计划字段是否支持"关联治疗方案"

**Involves Phases:** 需求定义 → 架构设计 → 数据模型设计

---

### Pitfall 2: 忽视数据隔离导致患者信息泄露

**What goes wrong:** 多租户架构中，患者数据在租户间泄露。

**Why it happens:**
- 租户ID字段遗漏或可被SQL注入绕过
- 查询时未强制添加租户过滤条件
- 缓存key设计未考虑租户隔离
- 导出功能忽略租户边界

**Consequences:**
- 患者隐私泄露（敏感医疗信息）
- 违反《个人信息保护法》《数据安全法》
- 机构间数据混淆，医疗纠纷风险
- 声誉损失，机构合作终止

**Prevention:**
- 数据访问层强制注入租户ID（中间件拦截）
- 所有数据查询必须显式声明租户ID
- 缓存策略增加租户前缀
- 导出功能增加租户校验
- 测试阶段增加"跨租户数据访问"测试用例

**Detection:**
- 安全review检查点：数据访问层是否统一
- 自动化测试：尝试跨租户数据查询

**Involves Phases:** 架构设计 → 权限管理 → 安全审计

### Pitfall 3: 将"触点"与"诊疗记录"混淆

**What goes wrong:** 把医疗诊疗记录当作普通的服务触点处理，丢失临床数据完整性。

**Why it happens:**
- 使用通用CRM的"互动记录"模型处理诊疗数据
- 未区分：咨询记录 vs 病历记录 vs 检查报告 vs 手术记录
- 缺乏医疗数据结构化设计

**Consequences:**
- 病历数据不完整，无法满足医疗质量评审
- 随访方案无法关联具体诊疗阶段
- 后续健康管理中心无法获取有效数据
- 违反《医疗机构病历管理规定》

**Prevention:**
- 区分"服务触点"和"医疗记录"的数据模型
- 诊疗记录采用结构化字段（症状、诊断、治疗方案）
- 服务触点记录非医疗信息（预约、满意度调查等）
- 设计触点类型枚举，明确每种类型的数据要求

**Detection:**
- 数据模型中是否区分"触点类型"
- 诊疗相关记录是否有完整的字段结构

**Involves Phases:** 需求分析 → 数据模型设计

### Pitfall 4: 随访系统成为"摆设"

**What goes wrong:** 随访功能无法真正落地，变成形式化的功能。

**Why it happens:**
- 随访计划与患者实际治疗方案脱节
- 医生缺乏执行随访的时间和信息
- 随访提醒未嵌入医生工作流
- 未区分不同类型随访（治疗中随访、治疗后关怀、复诊提醒）

**Consequences:**
- 治疗完成率数据失真
- 患者体验下降（感觉被忽视）
- 错过最佳干预时机（并发症早期发现）
- 系统使用率低，成为"僵尸功能"

**Prevention:**
- 随访计划必须关联具体治疗方案/技术路径
- 设计"一键执行随访"减少医生操作成本
- 随访提醒集成到医生日常工作提醒
- 分层随访：自动提醒 vs 人工跟进

**Detection:**
- 随访功能使用率是否被追踪
- 随访执行率是否达到预期

**Involves Phases:** 随访管理模块 → 触点管理 → 集成实施

### Pitfall 5: 集成HIS系统时低估接口复杂性

**What goes wrong:** 与HIS系统集成时，预估工作量严重不足，导致项目延期。

**Why it happens:**
- 低估HIS系统接口的文档缺失和变更频率
- 未考虑HIS厂商配合度和接口调试时间
- 假设标准接口实际需要定制开发
- 未考虑HIS系统运维时间段（通常夜间）

**Consequences:**
- 项目里程碑延误
- 集成预算超支
- 多机构部署时重复适配工作
- 等待HIS接口成为研发阻塞点

**Prevention:**
- 集成工作单独列为"风险项"，预留2-3倍缓冲时间
- 接口规范要求写入合同（数据格式、响应时间、SLA）
- 尽早搭建Mock Server进行并行开发
- 设计"降级方案"：无HIS集成时系统仍可基本运行

**Detection:**
- 集成计划是否包含Buffer时间
- 是否有Mock Server或替代方案

**Involves Phases:** 系统集成规划 → API开发 → 联调测试

## Moderate Pitfalls

### Pitfall 6: 权限模型过于复杂导致使用困难

**What goes wrong:** 精细化的权限设计反而导致日常使用困难，医生抵触系统。

**Why it happens:**
- 角色划分过细（科室、职务、操作类型多维度组合）
- 权限配置页面深藏三级菜单以上
- 新增功能时需要同时配置多个权限点
- 缺乏"权限继承"或"权限模板"

**Consequences:**
- 管理员配置和维护成本高
- 医生获得正确权限流程长
- 权限配置错误导致功能不可用
- 用户培训成本增加

**Prevention:**
- 角色设计采用"岗位+机构"两维度
- 提供"权限模板"快速分配
- 权限变更支持"申请-审批"工作流
- 权限配置界面暴露在显眼位置

**Detection:**
- 新增一个科室护士长权限需要几步操作
- 权限配置文档是否超过5页

**Involves Phases:** 权限管理 → 用户管理 → 实施部署

### Pitfall 7: 忽视操作审计导致合规风险

**What goes wrong:** 医疗操作需要可追溯，但审计日志不完整或不安全。

**Why it happens:**
- 审计日志分散在多个表或服务中
- 关键操作（如病历修改、数据删除）未记录变更前后状态
- 审计日志与业务数据共用存储，可被篡改
- 日志保留周期不符合法规要求

**Consequences:**
- 医疗纠纷时无法提供关键证据
- 违反《电子病历应用管理规范》
- 数据修改无法溯源
- 合规审查通不过

**Prevention:**
- 独立审计日志服务，写入后不可修改
- 记录：操作人、时间、IP、操作类型、变更前后数据
- 医疗核心操作（如病历修改）增加"原因选择"必填
- 日志保留至少15年（参照病历管理规范）

**Detection:**
- 审计日志是否防篡改
- 病历修改操作是否有完整变更记录

**Involves Phases:** 权限管理 → 操作审计 → 安全加固

---

### Pitfall 8: 性能测试场景脱离实际

**What goes wrong:** 性能测试通过但上线后卡顿，用户抱怨页面加载慢。

**Why it happens:**
- 性能测试只做简单CRUD，未模拟复杂查询场景
- 未考虑"患者旅程中心"等聚合报表的N+1查询问题
- 未测试100+并发下的真实用户体验
- 缓存策略未在实际数据量下验证

**Consequences:**
- 日常查询操作超时
- 报表页面长时间loading
- 医生等待时间长，工作效率下降
- 用户对系统失去信任

**Prevention:**
- 基于PRD中的数据容量目标（100万+患者）设计压测数据
- 重点测试：患者搜索、触点查询、随访列表等高频操作
- 包含"慢查询"的性能预算（查询≤1秒）
- 建立性能回归测试，CI/CD中集成

**Detection:**
- 压测报告是否包含实际业务场景
- 查询性能是否设置SLO

**Involves Phases:** 性能测试 → 优化迭代 → 上线准备

## Minor Pitfalls

### Pitfall 9: 多机构配置缺乏"继承"机制

**What goes wrong:** 多门店部署时，配置工作重复且难以统一管理。

**Why it happens:**
- 每个机构独立配置相同的基础数据（科室、岗位等）
- 总部更新配置时无法同步到各机构
- 缺乏"机构分组"概念

**Consequences:**
- 配置维护成本随机构数线性增长
- 机构间数据不一致
- 新机构接入周期长

**Prevention:**
- 设计"机构分组"模型：集团 → 分组 → 机构
- 配置分两类：全局配置（继承）vs 机构配置（覆盖）
- 提供"批量配置"功能

**Detection:**
- 新增一个机构需要手动配置多少项
- 总部更新时各机构是否需要单独操作

**Involves Phases:** 机构管理 → 多租户设计 → 实施流程

---

### Pitfall 10: 患者唯一标识设计不当

**What goes wrong:** 患者合并或身份核验时数据关联出问题。

**Why it happens:**
- 仅用手机号作为患者唯一标识
- 未考虑患者信息填写错误、变更手机等场景
- 缺乏"患者合并"机制
- 跨机构患者未建立关联

**Consequences:**
- 同一患者产生多条记录，诊疗历史断裂
- 患者合并时数据丢失
- 无法支持家庭账户等业务场景

**Prevention:**
- 设计多因素患者标识：身份证号 + 手机号 + 姓名 + 生日
- 提供"患者合并"功能（保留主记录，关联副记录）
- 变更手机号时保留历史记录
- 支持家庭成员关联

**Detection:**
- 患者数据中是否有重复记录检测
- 患者合并操作是否有完整的数据迁移逻辑

**Involves Phases:** 患者管理 → 数据模型 → 业务流程

## Phase-Specific Warnings

| 阶段 | 高危陷阱 | 缓解策略 |
|------|----------|----------|
| 需求定义 | Pitfall 1 (数据模型过度简化) | 邀请医疗业务专家参与数据模型review |
| 架构设计 | Pitfall 2 (数据隔离) | 数据访问层强制租户ID注入，安全review |
| 随访管理 | Pitfall 4 (随访成摆设) | 随访必须关联治疗方案，降低执行成本 |
| 系统集成 | Pitfall 5 (接口复杂性) | 预留3倍Buffer，Mock Server先行 |
| 权限管理 | Pitfall 6 & 7 (权限复杂/审计缺失) | 权限模板简化设计，独立审计日志服务 |
| 性能测试 | Pitfall 8 (脱离实际) | 基于实际数据量压测，建立性能SLO |
| 多机构部署 | Pitfall 9 (配置重复) | 机构分组+继承机制 |
| 患者管理 | Pitfall 10 (唯一标识) | 多因素标识，支持合并功能 |

## 为什么这些陷阱是医疗CRM特异的

| 陷阱 | 通用CRM | 医疗CRM特有原因 |
|------|---------|-----------------|
| 数据模型简化 | 会丢失客户洞察 | 危及患者安全，违反医疗法规 |
| 数据泄露 | 商业机密泄露 | 医疗隐私敏感度高，法律责任重 |
| 触点/诊疗混淆 | N/A | 病历有法律效力，必须完整合规 |
| 随访成摆设 | 客户流失 | 治疗完成率直接影响患者健康 |
| HIS集成复杂 | 系统对接困难 | 医疗系统标准化程度低，厂商配合度不可控 |
| 操作审计缺失 | 合规风险 | 医疗操作可追溯是法规要求 |
